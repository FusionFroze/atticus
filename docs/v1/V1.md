# Atticus v1 — locked implementation plan

Decisions in this file are **frozen**. Implement them; do not reopen them in a chunk chat. If one looks wrong once you're in the code, stop and say so rather than working around it.

**Scope in one line.** One Cloudflare Worker on the free tier that watches an Android app's Google Play reviews, posts each new or edited written review to a Discord channel within about 15 minutes, lets allow-listed people reply from Discord (button → modal → published on Google Play), and posts a weekly digest. First user: Lune (`com.fusionfroze.Lune`).

**What Atticus is.** The name (V3). "Atticus" is the product, the repo (`fusionfroze/atticus`), the `package.json` name and the Worker (`atticus`, and `atticus-dev` for testing). The spec's working name `play-reviews-bot` is retired.

## How to work on this

**Branch.** Everything happens on **`main`**: nothing is released, and there is no one else to protect `main` from. Each chunk is **one commit**, prefixed `v1(N):` (for example `v1(1): scaffold, config, Play read path`). **Always ask before committing.** Never create a branch without asking.

The work runs in order, chunks **v1-1 to v1-8**. Each chunk is implemented in **its own chat**, with a human review between chunks. Nothing is carried in a chat's head: every fact a later chunk needs lives in this repo.

**Starting a chunk chat.** `AGENTS.md` / `CLAUDE.md` point every chat here. Paste the kickoff block at the top of `chunks/v1-N.md`:

- A chunk chat **may not reopen a locked decision**. If one looks wrong, stop and say so.

## Platform facts that shape the design

Verified 2026-10-18 against the official docs. Re-verify the ones your chunk depends on; APIs drift. Google Play facts are in `SPEC.md` §5 and still stand.

**Cloudflare Workers, free plan** (https://developers.cloudflare.com/workers/platform/limits/):

| Limit | Value | What it means for us |
| --- | --- | --- |
| CPU time per cron run or HTTP request | 10 ms | Waiting on `fetch` and D1 doesn't count. RSA signing and Ed25519 are native WebCrypto, so they're cheap, but JSON work on big pages and rendering must stay lean. Measured in v1-1 and v1-4. |
| Subrequests per invocation (external `fetch`) | 50 | **The hard ceiling.** A first-run backfill or a burst of reviews can't all be posted in one run. Hence the shared run budget (V23). |
| Subrequests to Cloudflare services (D1) | 1,000 | D1 queries are not the bottleneck, but batch them anyway. |
| Cron triggers per account | 5 | We use **one** (V30). |
| Cron wall time | 15 min | Matches the 15-minute interval; the lease (V24) expires before the next run. |
| `waitUntil` after a response | up to 30 s | Enough for the Play reply and the message edit (V53). |
| Requests per day | 100,000 | Nowhere near. |

**Discord** (https://discord.com/developers/docs):

- **Create message** takes `nonce` (string, up to 25 characters) and `enforce_nonce`. With both set, a second create with the same nonce from the same author "in the past few minutes" returns the first message instead of creating a new one. This is our double-post guard (V22).
- **`allowed_mentions`**: without it, every mention in the content is parsed. Review text is user-written, so a review containing `@everyone` must never ping (V43).
- **Components V2** (flag `IS_COMPONENTS_V2`, `1 << 15`): such a message may only contain `components`; `content` and `embeds` fail with 400. The flag can be set on edit but never unset. This matters for the look decision (V41).
- **`custom_id`**: 1 to 100 characters on every interactive component (V25).
- **Modals**: a Text Input belongs inside a **Label** component (type 18). Text Inputs in an Action Row are deprecated, and the Text Input's own `label` is deprecated in favour of the Label's `label` and `description`. `max_length` is up to 4000; we use 350 (V52). This supersedes the modal wording in `SPEC.md` §5.
- Interactions: Ed25519-signed, `PING` → `PONG`, answer within 3 s, the interaction token is valid for 15 minutes (`SPEC.md` §5). When you save the Interactions Endpoint URL, Discord sends a `PING` and also a request with a bad signature, and expects `401` for it.

## Locked decisions

### Foundations

#### V1 — One Worker, free tier, self-hosted.

One Cloudflare Worker (`scheduled()` and `fetch()`), one D1 database, secrets via `wrangler secret put`. No other server, queue, KV namespace or paid feature. Each user deploys their own copy with their own credentials; Atticus never holds anyone else's. (`SPEC.md` §4, unchanged.)

#### V2 — Zero runtime dependencies.

The deployed bundle contains only our code.

- **Google auth:** RS256 JWT signed with WebCrypto (`crypto.subtle.importKey("pkcs8", …, { name: "RSASSA-PKCS1-v1_5", hash: "SHA-256" })`), exchanged at `https://oauth2.googleapis.com/token`. No `googleapis`, no JWT library.
- **Discord verification:** Ed25519 with WebCrypto (`{ name: "Ed25519" }`). No `discord-interactions`, no `tweetnacl`.
- **Routing:** a plain `if` on method and path. No router.
- **Config validation:** a small hand-written parser. No zod, no valibot.

Allowed as **dev dependencies** (each confirmed once with the user in v1-1): `wrangler`, `typescript`, `vitest`, `@cloudflare/vitest-pool-workers`, `@cloudflare/workers-types` (or generated types via `wrangler types`), `@biomejs/biome`, `discord-api-types` (types only, never imported as a value).

**Why:** nothing to audit or update, a tiny bundle (which helps the 10 ms CPU budget and startup), and code an open-source contributor can read end to end.

#### V3 — The name is Atticus.

User decision, 2026-10-18. Repo `fusionfroze/atticus`, `package.json` `"name": "atticus"` with `"private": true` (users deploy by cloning, not from npm; the unscoped npm name `atticus` is taken by an empty 2022 package, and `@fusionfroze/atticus` is free if a CLI ever ships). Workers `atticus` (production) and `atticus-dev` (testing). The repo description carries a descriptive tagline (Copy) because "atticus" alone is crowded in search.

#### V4 — TypeScript, strict, small.

TypeScript with `strict: true` and `noUncheckedIndexedAccess: true`. ES modules. No classes where a function and a type will do. Files stay small; a file passing ~300 lines is a sign to split along an existing boundary. Comments state constraints the code can't show, nothing else.

#### V5 — Repo and visibility.

User decision, 2026-10-18. Git on `main`, one commit per chunk, ask before committing. The GitHub repo `fusionfroze/atticus` is **private** during the build and becomes **public at v1.0.0** (v1-8), after a full-history secrets scan. MIT licence (added in v1-7).

### Configuration

#### V10 — The config shape: one `APPS` list plus flat globals.

User decision, 2026-10-18. Wrangler `vars` accept JSON values, so the per-app settings live in one structured var and everything global stays flat. Adding per-app channels, the App Store or Telegram later adds **fields**, not new variables.

`wrangler.jsonc` (illustrative; the exact file is written in v1-1):

```jsonc
{
  "name": "atticus",
  "main": "src/index.ts",
  "triggers": { "crons": ["*/15 * * * *"] },
  "d1_databases": [{ "binding": "DB", "database_name": "atticus", "database_id": "…", "migrations_dir": "migrations" }],
  "vars": {
    "APPS": [
      { "store": "play", "id": "com.fusionfroze.Lune", "name": "Lune", "consoleUrl": "https://play.google.com/console/…" }
    ],
    "DISCORD_APPLICATION_ID": "…",
    "DISCORD_PUBLIC_KEY": "…",
    "DISCORD_CHANNEL_ID": "…",
    "ALLOWED_USER_IDS": "123456789012345678",
    "TIMEZONE": "Asia/Kolkata"
```

**`APPS`** (var, required): a non-empty JSON array. Each entry:

| Field | Required | Notes |
| --- | --- | --- |
| `store` | ✓ | `"play"` is the only value in v1. Anything else is a config error naming the supported values. |
| `id` | ✓ | The package name. Unique within `APPS`. |
| `name` | | Display name in messages and the digest. Defaults to `id`. |
| `consoleUrl` | | Target of the "Open in Play Console" link button. Must be `https://`. No button when unset. Replaces the spec's global `PLAY_CONSOLE_URL`. |

Unknown fields are a config error (catches typos such as `consoleURL`). Future fields (`channelId`, `appStoreId`, …) are added by their own feature doc.

**Globals:**

| Name | Kind | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | secret | ✓ | — | The full JSON key. Only `client_email` and `private_key` are read. |
| `DISCORD_BOT_TOKEN` | secret | ✓ | — | |
| `DISCORD_APPLICATION_ID` | var | ✓ | — | Snowflake. |
| `DISCORD_PUBLIC_KEY` | var | ✓ | — | 64 hex characters. Public, so a var. |
| `DISCORD_CHANNEL_ID` | var | ✓ | — | Snowflake. Where everything is posted in v1. |
| `ALLOWED_USER_IDS` | var | ✓ | — | Comma-separated snowflakes. **Never defaults to everyone**; empty is a config error. |
| `TRANSLATION_LANGUAGE` | var | | unset | BCP-47-ish code such as `en`. Unset: no translation. |
| `BACKFILL` | var | | `post` | `post` or `silent`. See V33. |
| `PING_ON_LOW_RATING` | var | | unset | `&<roleId>` for a role, `<userId>` for a user. Mentioned on 1–2★ only. |
| `TIMEZONE` | var | | `UTC` | IANA name. Validated with `Intl.DateTimeFormat`. |
| `DIGEST_ENABLED` | var | | `true` | |
| `DIGEST_DAY` | var | | `mon` | `mon` … `sun`. New (V71). |
| `DIGEST_HOUR` | var | | `9` | `0` … `23`, in `TIMEZONE`. New (V71). |
| `DRY_RUN` | var | | `false` | See V55. `true` on the dev environment. |

Booleans accept `true` / `false` only (as strings or JSON booleans). Snowflakes are 17–20 digits.

#### V11 — Validation: all errors at once, actionable, never echoing secrets.

- Config is parsed once per invocation into a typed `Config` (contract below). Parsing is a pure function of the env, fully unit-tested.
- It collects **every** problem, not just the first, and each message names the variable, says what's wrong and where to look: "`DISCORD_CHANNEL_ID` is missing. Set it in wrangler.jsonc → vars (README → Discord setup)."
- Messages never include a secret's value, or any part of it. For a malformed `GOOGLE_SERVICE_ACCOUNT_JSON`, say which field is missing, not what was there.
- **When config is invalid:** `scheduled()` logs one `config_invalid` event with the list and does nothing else. `fetch()` returns `500` with a generic body for `/interactions` (the details are in the log). Atticus never tries to post a config error to Discord, because the Discord config may be the broken part.

### Storage and delivery

#### V20 — D1 only.

One D1 database, binding `DB`. No KV. All state lives in four tables (the [Schema](#schema) contract): `reviews`, `messages`, `outbox`, `state`. All multi-row writes that must agree use `DB.batch()` (a single transaction).

#### V21 — Migrations, not a schema file.

`migrations/0001_init.sql` and onward, applied with `wrangler d1 migrations apply` (`--remote` for deployed databases). A deployed database is never edited by hand. A schema change in a later version is a new numbered migration, so existing users upgrade with one command.

#### V22 — The outbox: write first, send later, never twice.

User decision, 2026-10-18. Every Discord post or edit that the cron makes goes through the `outbox` table:

1. **Enqueue.** The poll writes the review row and its outbox row in **one batch**. If the Worker dies after that, the row is still `pending`; if it dies before, nothing was written and the next poll sees the review as new again.
2. **Send.** The sender claims `pending` rows whose `next_attempt_at ≤ now`, ordered by `sort_key` then `id`, and sends each one.
3. **Mark.** On success it writes, in one batch, the outbox row as `sent` and the `messages` mapping.
4. **Nonce.** Each create carries `nonce = "o" + outbox.id` with `enforce_nonce: true`. If the Worker dies between Discord accepting the message and step 3, the retry gets the same message back instead of a duplicate (Discord's window is "a few minutes", and the retry comes on the next run or sooner). Edits (`PATCH`) are naturally idempotent.
5. **Render at send time.** The message is rendered from the **current** review row, not a snapshot. So a review edited while its `review_new` is still pending is simply posted in its latest form.
6. **Coalesce on enqueue.** If a `review_new` for the review is still pending, an edit enqueues nothing extra. A pending `message_update` for the same review is not duplicated.
7. **Failures.** `429` → stop sending this run (V23). Network or `5xx` → `attempts + 1`, `next_attempt_at` backs off (1, 5, 15, 60 minutes), `failed` after 5 attempts. `400` → `failed` at once (a render bug; log it). `403` / `404` on the channel → stop sending this run and set `warn:discord_channel` (V60; logged only, since the channel is the thing that's broken). Every `failed` row is logged with its id and kind, never its content.
8. **Housekeeping.** `sent` and `failed` rows older than 30 days are deleted at the end of a poll.

**Why not a "posted" flag:** the flag leaves a crash window that double-posts; the outbox closes it with the nonce, and also gives the budget (V23), retries and rate limits one shared queue for free.

#### V23 — One run budget for external calls.

Every invocation creates one `Budget` (contract) for external `fetch` calls, capped at **45** of the 50 allowed, leaving 5 for safety. Every Google and Discord call goes through it. The cron spends it in this order: the Google token (when not cached), the Play pages for each app (V31), then the sender, which stops when the budget is empty, on a Discord `429`, or after **60 s** of wall time. Whatever is left stays `pending` for the next run. An integration test asserts no run ever makes more than 45 external calls.

#### V24 — A lease so runs never overlap.

The cron takes a lease in `state` (`key = 'lease'`) with a conditional write: it succeeds only if there's no lease or the existing one has expired. The lease lasts **10 minutes** and is released at the end of the run (in a `finally`). A run that can't take it logs `run_skipped_locked` and exits. Interactions don't take the lease (V53).

#### V25 — A numeric id per review, used in `custom_id`.

`reviews.id INTEGER PRIMARY KEY`, with `UNIQUE (store, app_id, review_id)`. Discord components carry this short id, never the Play review id (which, with a package name, can approach the 100-character limit). Formats (contract): `reply:{id}` for the button, `reply-modal:{id}` for the modal, `reply-text` for the input.

#### V26 — The Google access token is cached in memory.

The token lives in a module-level cache keyed by `client_email` and is refreshed 5 minutes before expiry. It is **not** written to D1: a live access token is a credential, and keeping it out of storage keeps V1's "secrets only via `wrangler secret`" literal. Isolates are often reused across runs, so most runs don't sign; a cold isolate signs once (native RSA, about a millisecond). **If v1-1's CPU measurement shows signing is a problem**, the chunk stops and asks whether to cache in D1 instead.

### Polling and diffing

#### V30 — One cron, every 15 minutes, does everything.

User decision, 2026-10-18. `triggers.crons = ["*/15 * * * *"]`. Each run, in order, under the lease: poll every app (V31–V33) → check whether a digest is due (V71) → send the outbox (V22) → housekeeping. The interval may later be changed by the user within 5–30 minutes (`SPEC.md` §17); nothing in the code assumes 15.

#### V31 — Polling Play.

For each app in `APPS`: `GET …/reviews?maxResults=100` (plus `translationLanguage` when set), following `tokenPagination.nextPageToken` until there is none, **at most 5 pages** per app per run (500 reviews; the cap protects the budget, and a cut-off is logged as `poll_truncated`). Results are normalised into `Review` (V40's contract) inside `sources/play/`. Play `429` or `5xx`: skip that app this run, log, and carry on with the next (the 7-day window is forgiving). `401` / `403`: skip and raise the matching warning (V60).

#### V32 — The diff rules.

`core/diff` is a pure function from (the stored row or nothing, the fetched `Review`) to one outcome. Precisely:

| Stored | Fetched | Outcome | Writes | Enqueues |
| --- | --- | --- | --- | --- |
| none | any | **new** | insert the row (`first_seen_at = now`) | `review_new` (unless first run, V33) |
| row | `modifiedAt` greater | **edited** | update the row; `previous_rating` = the old rating; the reply stays as Play reports it | `review_edited` (coalesced, V22) |
| row, reply via bot | same `modifiedAt`, developer reply **text equal** to ours | **own reply seen** | update `reply_modified_at` only | nothing |
| row | same `modifiedAt`, developer reply differs from the stored one (new, changed or different text) | **replied elsewhere** | reply fields, `replied_via = 'external'`, `replied_by = null` | `message_update` |
| row with a reply | same `modifiedAt`, no developer reply | **reply removed** | clear the reply fields | `message_update` |
| row | same | **unchanged** | nothing | nothing |

Reviews that drop out of the API's 7-day window are left alone; that's expected, and a review the user deleted can't be told apart from one that aged out (a limitation for the README). `thumbsUp` changes alone are stored silently.

#### V33 — First run, per app.

An app's first successful poll is detected by `state` key `app_seen:{store}:{id}` (not a global flag, so adding a second app later backfills only that app). On that run:

- `BACKFILL=post` (default): every review found is enqueued oldest first, after the Connected message.
- `BACKFILL=silent`: the reviews are stored without enqueuing.
- In every mode, **one Connected message** per app is enqueued with `sort_key = 0`, so it's posted before the backfill. It says how many written reviews were found (Copy).

`BACKFILL=summary` from `SPEC.md` §8.2 was dropped in v1-2. `post` and `silent` remain. The Connected message carries the count in both (see the deviation).

#### V34 — Order.

Review messages are posted **oldest first** by `modifiedAt`, so the channel reads chronologically, across apps.

### The review model and its adapters

#### V40 — A `sources/` adapter per store, mirroring `notifiers/`.

Approved with the plan, 2026-10-18. Everything about Play's raw JSON, auth and endpoints lives in `sources/play/`, **including** normalisation into `Review`. `core/` never sees a store's raw shape. App Store reviews (v2) become `sources/appstore/`, implementing the same `ReviewSource` interface (contract). `SPEC.md` §6 put normalisation in `core/`; this moves it one boundary over so `core/` stays store-agnostic (see the deviation).

#### V41 — The Discord look is decided on real messages.

User decision, 2026-10-18. v1-3 posts **classic embeds** and **Components V2** versions of the same real Lune reviews into the test channel, and the user picks one, then iterates the details (colour, title, fields, footer, buttons, truncation). The approved values are **locked values** in the v1-3 log. The spec's §8.3 layout is the starting proposal, not a requirement. Whatever is chosen must hold: colour by rating (1–2 red, 3 amber, 4–5 green), the stars and rating in the title, the body truncated safely to Discord's limits, a clear "translated" signal when it is, and the author or "Anonymous".

#### V42 — Buttons live only on a review's latest message.

The latest message for a review has the buttons: **Reply** (primary) when there is no reply, or every known reply time is older than the review; **Edit reply** (secondary) when a reply is current or has no timestamp. **Open in Play Console** (link) when `consoleUrl` is set. When a newer message for the same review is posted (an edit), the older one keeps its text, drops its buttons, and points to the newer one. `messages.is_latest` tracks this.

#### V43 — No unintended pings, ever.

Every message Atticus sends sets `allowed_mentions`. By default it's `{ "parse": [] }`, so nothing in review text, author names or replies can ping anyone. The only exception is `PING_ON_LOW_RATING`: on a 1–2★ new or edited review, that single role or user is listed explicitly in `allowed_mentions.roles` or `.users`, and its mention is placed in `content`.

#### V44 — Discord REST only.

Bot token, API v10, `https://discord.com/api/v10`. No gateway connection. A `User-Agent` of `DiscordBot (https://github.com/fusionfroze/atticus, <version>)`.

### Interactions and the reply flow

#### V50 — One route.

`POST /interactions` is the only route. Everything else is `404` with an empty body. No status page in v1 (that's `/reviews status` in v1.1).

#### V51 — Verify, then check who and where.

1. **Signature first.** Read the raw body, verify `X-Signature-Ed25519` over `X-Signature-Timestamp + body` with `DISCORD_PUBLIC_KEY`, before parsing JSON. Missing or invalid → `401`, empty body.
2. `PING` → `PONG`.
3. **Allow-list.** The acting user (`member.user.id`, or `user.id` in DMs) must be in `ALLOWED_USER_IDS`. Otherwise an ephemeral refusal (Copy), and nothing else happens.
4. **Channel.** The interaction must come from `DISCORD_CHANNEL_ID`. Otherwise an ephemeral refusal. This stops a stray copy of a message in another server from being used.
5. Unknown `custom_id` or type → an ephemeral "not supported" message, logged.

Whether to also reject stale timestamps (a replay window) is an [open item](#open-items) for v1-4.

#### V52 — The reply modal.

The button `reply:{id}` answers with a `MODAL` (`custom_id = reply-modal:{id}`): a title with the author and rating (Copy), one **Label** wrapping a paragraph Text Input (`custom_id = reply-text`, `max_length: 350`, `min_length: 1`, required), with the "public on Google Play" hint as the Label's description. For **Edit reply**, the input is prefilled with the stored reply, and the hint adds that editing doesn't notify the reviewer (Copy). The review's data is read from D1 by id; a missing row → ephemeral error.

#### V53 — Submitting: defer, then publish in `waitUntil`.

1. Re-check the allow-list and channel, and re-check the trimmed text is 1–350 characters (an ephemeral error if not; nothing is sent).
2. Answer at once with `DEFERRED_UPDATE_MESSAGE`.
3. In `ctx.waitUntil`: `ReviewSource.reply` → on success, one D1 batch (`reply_text`, `reply_modified_at`, `replied_via = 'bot'`, `replied_by`, `replied_at`) → edit the original message through the interaction webhook (`PATCH /webhooks/{application_id}/{token}/messages/@original`) to show the reply and swap the button to Edit reply.
4. On failure: an **ephemeral follow-up** with a human message per cause (Copy: too long, review gone, permission missing → setup docs, Google auth, rate limited, anything else), and the message is left as it was.
5. A reply POST is **never retried automatically**. A double submit only replaces the reply with the same text; it's logged as `reply_duplicate`.

Interactions don't take the cron lease. The cron recognises the bot's own reply by its text (V32), so the two can't fight.

#### V54 — Humans write every reply.

Atticus never generates, suggests or auto-posts reply text in v1. AI drafts (v2) will only pre-fill the modal. (`SPEC.md` §4, unchanged.)

#### V55 — `DRY_RUN`.

With `DRY_RUN=true`, the submit flow does everything except the Play `POST`: it logs `reply_dry_run`, **does not change D1**, and edits the Discord message to show the text with a clear "Dry run, not published" marker (Copy). D1 stays untouched so the next poll doesn't see a "reply removed". The dev environment sets `DRY_RUN=true`; turning it off there is a user decision per real reply (V82).

### Health and errors

#### V60 — Warnings are posted once and cleared once.

Each kind of persistent failure has a `state` flag `warn:{kind}[:{appId}]`: `google_auth` (token exchange fails or `401`), `play_forbidden:{appId}` (`403`, usually permissions not yet propagated or not granted), `discord_channel` (`403` / `404` posting; logged only, since we can't post). The first failure enqueues **one** warning message pointing at the README's troubleshooting section and sets the flag. While the flag is set, nothing more is posted for it. The first success after that clears the flag and enqueues one short "back to normal" message (Copy). Everything is also logged.

#### V61 — Deleted messages are replaced.

If editing a review's message returns `404` (someone deleted it), the review's current state is posted as a fresh message, which becomes its latest.

#### V62 — Structured logs, no content.

`console.log(JSON.stringify({ event, … }))` with `event` plus, where relevant, `appId`, `reviewId`, `outboxId`, `status`, `durationMs`. **Never** review text, author names, reply text, tokens, keys or full Google/Discord error bodies (log the status and Google's error `reason` only). The events are listed in the contract and grow by chunk.

### The weekly digest

#### V70 — Content.

Built from D1, one message per app (resolved in v1-6: one per app, not a combined message), covering the 7 days ending at the run. The starting proposal is `SPEC.md` §8.5: counts of new and edited written reviews, the average rating with the change from the previous week, a 1–5 distribution, reply rate and median time to reply (bot replies, from `first_seen_at` to `replied_at`), a breakdown by app version, and the three lowest-rated unanswered reviews with links to their messages. It's always labelled **"written reviews only"** (Copy). The look was locked in v1-6 (Copy).

#### V71 — When: a local-time check inside the 15-minute cron.

User decision, 2026-10-18. Each run computes the most recent scheduled moment (`DIGEST_DAY` at `DIGEST_HOUR:00` in `TIMEZONE`, via `Intl.DateTimeFormat`) at or before now. If `state.digest_last` isn't that moment's local date, and the moment is less than 24 hours ago, the digest is enqueued and `digest_last` set in the same batch. More than 24 hours late (a long outage) → that week is skipped and logged. This handles DST, needs no UTC conversion by the user, catches up after a missed run, and uses no extra cron trigger.

### Process

#### V80 — Two environments, two Discord applications.

- **`atticus-dev`** (wrangler `env.dev`): its own D1 database `atticus-dev`, its own Discord application ("Atticus Dev") whose Interactions Endpoint is the dev Worker, a **test channel** in a test server (or a private channel the user chooses), `DRY_RUN=true`. It polls Lune's real reviews with the same service account. Every chunk from v1-2 to v1-6 is verified here.
- **`atticus`** (top level): the production Worker for Lune with its own D1 database and its own Discord application, set up in v1-7 by following the README, which is how the README gets tested.

Interactions need a public HTTPS URL, which is why testing is on the deployed dev Worker rather than a tunnel.

#### V81 — Looks are decided in the test channel.

Like Lune's device iteration: a chunk posts real variants, the user judges them in the Discord client (desktop **and** mobile, light and dark theme), one question at a time, at most two or three alternatives side by side. The locked values go in the chunk log.

#### V82 — Real replies only with a go-ahead.

A reply that would actually publish on Google Play happens only when the user has picked the review and approved the text in that conversation. v1-4 does exactly one, on a review the user chooses.

## Smokes

Run the ones that apply whenever a chunk touches them. Tick what applies, and write what was skipped. The standing ones are repeated in `docs/ARCHITECTURE.md`.

- [ ] **Signature.** A bad or missing signature → `401`. `PING` → `PONG`. Discord accepts the Interactions Endpoint URL.
- [ ] **Allow-list.** A user not on the list clicks Reply → an ephemeral refusal, no modal, nothing in D1.
- [ ] **No double posts.** Two cron runs back to back → no duplicate messages. A crash between sending and marking (integration test with a fault injected) → one message.
- [ ] **No pings.** A review whose text contains `@everyone` and `<@id>` → posted, nobody pinged.
- [ ] **Budget.** The integration test asserts ≤ 45 external calls per run, with a backfill of 200 reviews; the rest drain over later runs, oldest first.
- [ ] **Logs are clean.** `wrangler tail` during a run and a reply shows no review text, author names, reply text or tokens.
- [ ] **CPU.** `wrangler tail` shows each cron run and each interaction under 10 ms CPU in normal use. Record the numbers.
- [ ] **The reply flow** (v1-4 on): Reply → modal → submit (dry run) → the message shows it; Edit reply → prefilled; each error path's message.
- [ ] **Reflections** (v1-5 on): an edit in Play Console shows up; a reply removed in Play Console shows up; a deleted message is reposted.
- [ ] **Config.** Each required var removed in turn → a clear `config_invalid` naming it; no secret value in the output.

### v1-6 — Weekly digest

One digest per app. A quiet week still posts "No written reviews this week." The written-reviews label stays above that line. Both were the open items; the user chose them with the plan.

**Schedule.** Each run finds the latest `DIGEST_DAY` at `DIGEST_HOUR:00` in `TIMEZONE` at or before now. `Intl` only formats an instant, so the instant is probed. A missing hour uses the previous week's slot. An hour that exists twice uses the later instant that is still at or before now. `digest_last` is that instant's `YYYY-MM-DD`. The digest is due when that date differs and the slot is under 24 hours old. Exactly 24 hours is late: set `digest_last`, log `digest_skipped` once, and enqueue nothing. The same local date does nothing and logs nothing. `DIGEST_ENABLED` false returns before any read or log.

**Window.** 7 × 24 hours of epoch time, half-open, ending at the run. The outbox payload is `{"appId","windowEnd"}` only, and `sort_key` is `windowEnd`. A send that waits uses that stored end. New means `first_seen_at` in the window. Edited means `first_seen_at` before the window and `modified_at` inside it. A review that arrives and is edited in the same week counts as new only. Averages, the distribution, reply rate, versions, and the lowest three use this week's new reviews and the current rating. The change from last week is omitted when either week has no new reviews. Reply rate counts bot and external replies. The median is bot replies only. The read does not select author, body, or reply text.

**Message.** A Components V2 container, no accent. `allowed_mentions.parse` is empty. The text is rendered when the row is sent. A guild id from the create response is saved as `discord_guild`. If it is missing and a lowest unanswered review has a title and a message, one budgeted channel GET fills the link.
